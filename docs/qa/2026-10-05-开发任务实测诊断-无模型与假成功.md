# 小U 开发任务实测诊断：为什么没有 WorkBuddy 式的"分析→工作→检测→再操作"闭环

- 诊断时间：2026-10-05 13:57
- 诊断方式：真机日志 + 产物实盘 + 源码行号取证（不靠推测）
- 实测版本：0.31.21（用户 13:46 启动，13:51 结束）
- 用户诉求："打开小U 执行开发任务，感觉仍然没法像 WorkBuddy 一样分析、工作、检测、再操作"

---

## 一、结论先行

本次不是"小U 能力退化"，而是**两个叠加故障**：

1. **当场致命原因：模型层完全断链** —— DeepSeek API Key 失效（401），且本地无 Ollama，整个会话**一次模型都没成功调用过**。没有模型 = 没有思考，分析/规划/自我修正在物理上不可能发生。
2. **结构性根因：开发链路是"固定脚本流水线"而非"闭环"** —— 即使模型正常，代码也是按预定步骤走完并直接报成功，**没有"把结果回灌给模型 → 让模型自己判断 → 重做"的回路**。这才是"不像 WorkBuddy"的根本原因。

另有一个**恶劣缺陷**：生成失败时把错误文本当文件内容写盘，并记 `ok=true`、报"✅ 落盘 3 个文件"——**假成功**。

## 四、断点 3（最恶劣）：失败被伪装成成功

### 源码定位：`pasm/cognitive/coder.py:290-305`
```python
content = ""
try:
    content = _strip_fence(str(llm_fn(sys_p, hint, task="code") or ""))
except Exception as ex:
    content = "# 生成失败（%s）" % ex      # ← 291-294 行：异常被吞，错误文本当正文
if len(content) < 8:                       # 295 行：只查长度，不查是否为报错
    content = scaff.get(rel, "# 生成失败（内容过短）")
...
files_done.append({"path": rel, "scaffold": len(content) < 8 or rel in scaff})
```
三个问题叠加：
1. **异常被 `except` 吞掉**，错误信息直接成为文件内容；
2. **长度判据失效** —— `# 生成失败（401 ...）` 长度远超 8，`len(content) < 8` 不成立，
   于是**脚手架骨架也不会兜底**，错误文本被原样写进 `main.py`；
3. **`scaffold` 标记与 `ok` 判定没挂钩** —— 只要写了文件就算"完成"。

## 五、结构性根因：流水线 vs 闭环

### WorkBuddy 的做法（模型全程在环）
```
分析需求 → 选工具执行 → 读回真实结果 → 判断质量 → 不满足则带错误重做 ↺
```
关键：**执行结果会回灌给模型，模型看到自己"写错了"，自己决定改不改、怎么改**。

### 小U 当前的做法（固定脚本）
```
代码定流程 → 逐文件调模型 → 直接写盘 → 报成功
              ↓ 失败
         无分支（继续往下走）
```

### 本次实测三个能力全部缺席
| 能力 | WorkBuddy | 小U 本次 |
|---|---|---|
| 观察（结果回灌） | 有 | **无**：401 报错被当正文写进 main.py |
| 判断（质量校验） | 有 | **形同虚设**：`_smoke_one` 对 `# 生成失败(...)` 判过，记 `smoke ✓` |
| 重做（失败重试） | 有 | **无**：无"失败→重试/换栈/如实降级"分支 |

### 关键补充
`desktop/devloop.py` **已经实现了真正的闭环**（`agent_loop` / `build_fix_loop` /
`decompose` / `verify_project`）——本次之所以没生效，是因为第一步
`llm_fn` 就 401 崩了，压根没走到 devloop。**一旦模型可用，闭环才会真正启动。**

## 六、修复建议（按优先级）

### P0 —— 你现在就能做（30 秒）
1. 换有效 DeepSeek Key，或启动 Ollama + 填 `local_model`。
   **不做这步，后面一切验证都无从谈起。**
2. 顺手清掉 `D:\geo` 里的垃圾文件（3 个 401 文本 + `.pasm_dev.json`）。

### P0 —— 代码必须改（我建议立刻做）
3. **`coder.py:290-305` 假成功兜底**（最紧急）
   - 捕获到"无模型/鉴权类异常"时**立即中止整个生成**，返回
     `{"ok": False, "log": "模型不可用：<真实原因>"}`，**绝不写盘**；
   - 写盘前加**内容有效性判据**：内容以 `# 生成失败` 开头 / 含 `401` /
     `Traceback` / `Authentication` → 判失败，不写盘、不记 `ok=true`；
   - `scaffold` 兜底要**无条件生效**（当前被长度判据绕过）。
4. **模型不可用要在 UI 首屏可见**：启动即探测（探云端 1 次 + 探本地），
   不可用则顶部红条明示"未配置可用模型"，而不是让用户跑完任务才发现。
5. **selfheal 接入模型失败**：`record_build_issue` 补记"无模型/401"，
   `last_status()` 要能看到（当前 `errors:0` 完全失明）。

### P1 —— 架构对齐 WorkBuddy
6. **开发主路径切到 `devloop.agent_loop`**，把 `coder.gen_project` 降级为
   "仅在无工具链时的兜底"，而不是主流程。
7. **闭环三件套接线**：每步执行后把**真实结果（stdout/stderr/退出码）回灌**给模型，
   由模型决定"重做/换栈/降级说明"，代码不预设结论。
8. **引擎满载**：修 `pasm-desktop-light` 降级问题，让
   `metacognition`/`working_memory` 真正可用。

### P2 —— 体验
9. 任务进度文案禁止在无真实产物时报"✅ 落盘"；宁可显示"⚠ 模型不可用，未生成"。
10. 用户说"我全删了"时，应**先确认删除范围**（当前直接当新需求建项目）。

## 七、给用户的一句话

**不是小U变笨了，是它这次"没电"（模型 401 全程零调用）+ "灯坏了"（失败被报成成功）。**
先补上可用的模型，再把"失败必须如实上报"这个底线修好，闭环能力才能显出来。
在那之前，任何关于"它到底行不行"的判断都不成立——因为它一次都没真正思考过。
